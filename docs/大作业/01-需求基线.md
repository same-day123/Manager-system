## 1. 用户角色分析（Persona）

系统在实现上有 7 个角色，按**使用动机**归纳为 5 类 Persona。文档里写 5 类（任务书要求 ≥3）。

### P1 报修申请人

| 项目 | 描述 |
| --- | --- |
| 对应角色 | `student_assistant`（学生助管）、`room_keeper`（房间管理员） |
| 角色描述 | 实验室的日常使用者与兼职管理的学生，负责所在房间的设备日常巡视 |
| 核心目标 | 设备坏了能在 1 分钟内报上去，并且知道现在修到哪一步了 |
| 痛点 | 手抄设备编号容易抄错；报上去之后像掉进黑洞，得反复问管理员；修完了没人管质量好坏 |
| 数据可见范围 | **仅本人提交的报修单**（行级过滤强制生效） |

### P2 维修执行方

| 项目 | 描述 |
| --- | --- |
| 对应角色 | `repair_engineer`（维修工程师）、`teacher`（维修教师） |
| 角色描述 | 学校设备处或学院派驻的维修人员，同时带教 |
| 核心目标 | 一次看全所有待办工单，按故障等级排优先级；修完把成本如实登记 |
| 痛点 | 工单靠群消息派发，容易漏；不知道哪台设备是反复修的；费用记在本子上，学期末汇总不出来 |
| 数据可见范围 | 全部报修单 |

### P3 实验室管理员

| 项目 | 描述 |
| --- | --- |
| 对应角色 | `lab_manager`（实验室管理员） |
| 角色描述 | 学院实验室中心的在岗教师，对全院实验室资产与运维负总责 |
| 核心目标 | 台账准、工单闭环、随时能拿出运维数据向学院汇报 |
| 痛点 | 房间/资产/报修分散在三个 Excel 里，对不上；学生乱报修占用维修资源；上级要看数据时只能手工统计 |
| 数据可见范围 | 全部资产、全部报修、运维看板 |

### P4 资产管理员

| 项目 | 描述 |
| --- | --- |
| 对应角色 | `asset_keeper`（资产管理员） |
| 角色描述 | 负责固定资产卡片、盘点与报废手续的行政人员 |
| 核心目标 | 每台设备从入库到报废的每一步变动都有据可查；盘点时能一次导出全量台账 |
| 痛点 | 调拨、报废不留痕，账实不符时查不出责任环节；新购设备靠手工录入，一次几十台要录半天 |
| 数据可见范围 | 全部资产、全部报修（**只读**，无报修处理权） |

### P5 观察者与系统管理员

| 项目 | 描述 |
| --- | --- |
| 对应角色 | `lab_viewer`（实验室观察员）、`admin`（超级管理员） |
| 角色描述 | 观察员是学院督导/上级检查人员，只查不改；admin 负责账号与权限配置 |
| 核心目标 | 观察员：不动数据也能看清全院运维状况；admin：给不同岗位配不同角色，各人只看该看的 |
| 痛点 | 观察员：手工要数据太慢；admin：权限一旦配错会出现「按钮看得见但点下去 403」 |
| 数据可见范围 | 观察员：全部数据只读；admin：全量 |

## 3. 验收标准（GWT）

任务书要求至少为 5 个核心用户故事写 Given-When-Then。这里写 6 个。

### US-01 验收标准：扫码报修

**场景 1：扫码带出资产信息**
- **Given** 学生助管已登录，且该资产状态为「正常」
- **When** 该学生扫码打开报修页并提交故障描述
- **Then** 系统自动填充资产编号与名称，报修单状态为「待审核」，并生成一条「提交报修」的履历记录

**场景 2：扫码一台维修中的资产**
- **Given** 该资产状态已是「维修中」（前一张报修单还没结束）
- **When** 学生对该资产提交报修
- **Then** 系统提示「该资产当前不可报修」，不生成报修单

### US-03 验收标准：查看报修进度

**场景 1：正常查看**
- **Given** 存在一张已完成 3 次状态流转的报修单
- **When** 申请人打开该报修单详情
- **Then** 时间线按时间正序显示「提交报修 → 状态流转 → 状态流转 → 状态流转」，每条含操作人和操作时间

**场景 2：越权查看**
- **Given** 学生 A 登录，报修单由学生 B 提交，且 A 不是处理角色
- **When** A 直接访问该报修单详情接口
- **Then** 系统返回「没有权限访问该报修单」

### US-05 验收标准：维修工程师看全部工单

**场景 1：处理角色可见全量**
- **Given** 以 `repair_engineer` 登录，库中存在 3 个不同申请人提交的报修单
- **When** 打开报修列表
- **Then** 3 条全部可见

**场景 2：普通角色只能看自己**
- **Given** 以 `student_assistant` 登录，库中存在本人 1 条、他人 2 条报修单
- **When** 打开报修列表
- **Then** 只返回本人那 1 条

### US-08 验收标准：审核报修申请

**场景 1：审核通过**
- **Given** 报修单状态为「待审核」
- **When** 实验室管理员点「通过」
- **Then** 状态变为「待维修」，履历新增一条「状态流转」记录

**场景 2：拒绝**
- **Given** 报修单状态为「待审核」
- **When** 实验室管理员点「拒绝」
- **Then** 状态变为「已拒绝」，且该报修单关联的资产状态由「维修中」恢复为「正常」

**场景 3：跳过环节**
- **Given** 报修单状态为「待审核」
- **When** 试图直接把状态改成「已完成」
- **Then** 系统抛出「非法的报修状态流转」，数据不变

### US-09 验收标准：资产台账筛选导出

**场景 1：按房间筛选**
- **Given** 资产台账中存在房间 A 的 3 台、房间 B 的 2 台资产
- **When** 资产管理员筛选「房间＝A」并导出
- **Then** 导出的 Excel 只含 A 的 3 条记录

**场景 2：已删除资产不出现在导出结果**
- **Given** 其中 1 台资产已被逻辑删除
- **When** 导出该房间资产
- **Then** 结果只有 2 条

### US-12 验收标准：防止误删有资产的房间

**场景 1：房间下还有资产**
- **Given** 房间 A 下存在 2 台资产
- **When** 管理员删除房间 A
- **Then** 系统提示「实验室下存在资产，不能删除」，房间与资产均不受影响

**场景 2：房间已清空**
- **Given** 房间 B 下没有任何资产
- **When** 管理员删除房间 B
- **Then** 删除成功，且为逻辑删除（`del_flag = '2'`），数据库记录仍存在

## 4. 业务规则清单（**测试的 Oracle，T1/T2 直接引用**）

> 这一节是给测试用的。每条规则都写成**可被断言的形式**——断言什么、期望什么，一目了然。

### BR-01 报修状态机

```
允许的流转：
  0 待审核 ─审核通过→ 1 待维修 ─开始维修→ 2 维修中 ─维修完成→ 3 已完成
  0 待审核 ─拒绝────→ 4 已拒绝

禁止的流转（全部必须被拒绝）：
  0 → 2、0 → 3、0 → 4 之外的任何跳转
  1 → 0、1 → 3、1 → 4
  2 → 0、2 → 1、2 → 4
  3 → 任何状态
  4 → 任何状态
```

- 非法流转的期望行为：抛 `com.ruoyi.common.exception.ServiceException`，消息为「非法的报修状态流转」，且**数据库不变**
- 传 `null` 或与当前状态相同的状态：**不校验，直接放行**（视为非状态变更的普通更新）

### BR-02 资产状态联动

| 触发动作 | 资产状态变化 | 断言点 |
| --- | --- | --- |
| 提交报修成功 | 「正常」→「维修中」 | `lab_asset.status = '2'` |
| 报修单状态变为「已完成」 | 「维修中」→「正常」 | `lab_asset.status = '0'` |
| 报修单状态变为「已拒绝」 | 「维修中」→「正常」 | `lab_asset.status = '0'` |
| 删除「待审核」的报修单 | 「维修中」→「正常」 | `lab_asset.status = '0'` |
| 删除「已拒绝」的报修单 | **不变**（本来就是正常） | 不触发更新 |

### BR-03 权限规则

| 判定 | 角色白名单 | 不命中的后果 |
| --- | --- | --- |
| `canHandleRepair()` 可处理报修 | `admin`、`teacher`、`lab_manager`、`repair_engineer` | 列表被按「申请人＝自己」过滤；不能审核、不能改他人单据 |
| `canViewAll()` 可看全部数据 | 上述 4 个 + `asset_keeper`、`lab_viewer` | 列表与看板数据被强制过滤为「本人」 |
| 未登录 / 上下文缺失 | — | `canHandleRepair()` 与 `canViewAll()` **都返回 false**（权限收缩最安全，不能返回 true） |
| `admin` 内置用户 | — | 无视角色列表，两个判定都返回 true |

**唯一来源**：后端 `com.ruoyi.project.laboratory.util.LabRoleUtils`，前端 `src/utils/labPermission.js`。**任何测试都不得复制一份角色白名单**，必须调这两个工具类，否则口径会漂移。

### BR-04 事务边界

以下方法标注 `@Transactional(rollbackFor = Exception.class)`，**写操作必须整体成功或整体回滚**：

| 方法 | 事务内必须一起完成的事 | 断言方式 |
| --- | --- | --- |
| `insertLabRepair` | ① 插入报修单 ② 更新资产状态为维修中 ③ 插入报修履历 | 断言 3 张表都变了；模拟 ③ 失败时 ①② 也要回滚 |
| `updateLabRepair` | ① 更新报修单 ② 插入状态流转履历 ③ 若终态则恢复资产状态 | 同上 |
| `deleteLabRepairByRepairId` | ① 逻辑删除 ② 插入履历 ③ 若原状态为待审核则恢复资产 | 同上 |
| `insertLabAsset` | ① 插入资产 ② 插入「入库」履历 | 断言 2 张表都变了 |
| `importLabAsset` | 逐条独立提交；单条失败**不**影响其他条，最终返回失败汇总 | 断言成功数 + 失败数 = 总数 |

### BR-05 校验规则

| 对象 | 规则 | 期望异常消息 |
| --- | --- | --- |
| 报修单 | 必须选择资产 | 请选择报修资产 |
| 报修单 | 故障描述非空 | 故障描述不能为空 |
| 报修单 | 资产必须存在且未删除 | 资产不存在或已删除 |
| 报修单 | 资产状态必须是「正常」 | 该资产当前不可报修 |
| 报修单 | 评分必须在 1~5 之间（含边界） | 维修评分必须在1到5之间 |
| 报修单 | 只有「已完成」的单可评价 | 只能评价已完成的报修单 |
| 报修单 | 只有申请人本人可评价 | 只能评价本人提交的报修单 |
| 资产 | 资产编号非空 | 资产编号不能为空 |
| 资产 | 资产名称非空 | 资产名称不能为空 |
| 资产 | 必须归属某个实验室 | 所属实验室不能为空 |
| 资产 | 所属实验室必须存在 | 所属实验室不存在或已删除 |
| 资产 | 资产编号全局唯一 | 资产编号已存在 |
| 资产 | 资产编号唯一性校验要排除自身（更新场景） | 不应抛异常 |
| 资产 | 「维修中」的资产不能删除 | 资产维修中，不能删除 |
| 房间 | 房间编号非空 / 名称非空 | 实验室编号不能为空 / 实验室名称不能为空 |
| 房间 | 房间编号全局唯一 | 实验室编号已存在 |
| 房间 | 房间下有资产时不能删除 | 实验室下存在资产，不能删除 |

### BR-06 逻辑删除

- 资产、报修单、房间的删除**均为逻辑删除**，写 `del_flag = '2'`，**不做物理删除**
- 所有列表查询必须带 `del_flag = '0'` 条件，默认过滤已删除数据
- 断言方式：删除后直接查库，记录仍在且 `del_flag='2'`
