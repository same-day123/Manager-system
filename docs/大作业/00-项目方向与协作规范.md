## 2. 产品定位

**一句话定位**：面向高校二级学院实验室的「资产全生命周期 + 故障报修闭环」管理平台。

**要解决的真实痛点**（答辩讲这个，不要念文档）：

| 现状 | 后果 |
| --- | --- |
| 台账靠 Excel 手工维护 | 资产调拨、报废没有留痕，学期末账实不符，查不出是谁改的 |
| 报修靠微信群喊人 | 谁报的、谁在修、修到第几步全靠记忆，超时无人催办 |
| 没有统计数据 | 一学期修了多少次、哪台设备最常坏、维修费花了多少，完全说不清 |

**为什么值得做**：把「台账 + 工单 + 统计」三件事收进一个系统，让每次资产变动都有履历、每张报修单都有状态和责任人、每个学期都有可交付的运维数据。

## 6. 协作规范

### 6.1 派活格式

每张任务卡固定 7 段，**缺一段就退回**：

```
1. 目标            —— 一句话说清要达成什么
2. 交付内容        —— 具体文件与验收标准（可勾选）
3. 边界            —— 明确不许动什么，防止越界改坏已有功能
4. 提示词          —— 可直接复制给编码 Agent 的完整 Prompt
5. 执行指导与踩坑  —— 已知的技术陷阱、本机环境限制、参考文件
6. 验收方式        —— 跑什么命令、看什么结果
7. 留痕要求        —— 本卡要在 AI 留痕里记什么
```

### 6.2 AI 留痕（硬性，别偷懒）

任务书要求 AI 报告里必须有「**≥3 处完整提示词 + 生成结果**」和「**≥1 处 AI 代码人工审查修改点**」，还有一条红线：**查重率 >30% 该项 0 分**。

所以：**每完成一张任务卡，就在 `docs/大作业/AI留痕/` 下按下面的模板留一份记录。**

```markdown
## YYYY-MM-DD｜任务卡 T?_

- **AI 工具**：（Cursor / Claude Code / WorkBuddy / ……）
- **完整提示词**：（原样粘贴，不要摘要——AI 报告要的就是原文）
- **生成结果摘要**：生成了哪些文件、多少行、一次通过还是来回改了几轮
- **人工修改点**：改了什么 + 为什么改   ← **最重要**，AI 报告要 ≥1 处，多留几处备用
- **效率对比**：人工预估耗时 / AI 实际耗时 / 返工次数
- **截图**：提示词界面截图、生成结果截图、运行结果截图 → 存 `docs/大作业/AI留痕/截图/`
```

### 6.3 三条红线

1. **文档查重 >30%（含代码注释）→ 文档项 0 分。** 本目录下的提示词和任务卡是**给你派活用的**，任何一个段落都不许直接粘进最终交付文档。文档必须重写。
2. **代码注释不要大段抄若依官方注释**，也别把本目录的表格直接复制成文档章节。
3. **必须写 AI 使用声明**：最终文档里要明确哪几节由 AI 生成、哪几节人工重写。

最小代价方案，供应急。核心思路是**复用已验证的报修状态机，而不是新建一套逻辑**：

| 步骤 | 内容 | 复用点 |
| --- | --- | --- |
| 1 | 新增 `lab_reservation` 表（room_id / asset_id / applicant_id / start_time / end_time / status / audit_* ） | 照抄 `lab_repair` 的表结构命名习惯 |

| 3 | 时间段冲突校验：同房间 `[start,end)` 区间重叠即拒绝 | 一条 SQL 即可，是新增的**唯一**技术点 |

| 5 | 菜单/权限 | 追加 `laboratory:reservation:*` 权限 + 角色授权脚本 |

预估：一轮完整迭代（后端 + 前端 + SQL + 测试）。
**收益**：选题合规性 100%。**代价**：R4 文档轮次被压缩。
