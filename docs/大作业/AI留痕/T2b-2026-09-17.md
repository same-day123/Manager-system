### 3.3 H2 方言垫片：怎么让"跑不了的看板"跑起来的（**本轮的核心工程记录**）

**问题**：`LabDashboardMapper.xml` 的「近 7 天趋势」两条查询用了
`date_format(create_time, '%m-%d')` 与 `date_sub(curdate(), interval 6 day)`，**H2 1.4.199 两个函数都没有**。
前一轮（T2）的结论是"看板无法覆盖，记为 D-19 容忍"。

**本轮改判**：**不必容忍**。H2 支持 `create alias <名> for "<全限定类名>.<静态方法>"`——
**在测试库里注册两个同名函数，生产 SQL 一个字都不用改就能执行。**

**探针取证的三个版本（都留在 `.workbuddy/logs/` 里可复核）**：

| 版本 | 试了什么 | 结果 | 日志 |
| :-: | --- | --- | --- |
| v1 | 直接跑带 `date_format` 的 SQL | 失败：`Function "DATE_FORMAT" not found` | `h2-probe-dashboard.txt` |
| v2 | `create alias ... as $$ ... $$`（内联 Java 源码） | 探针脚本自己踩坑：用 `executeQuery` 跑 DDL 报 `Method is only allowed for a query`；改写后**内联形式可行**，但函数体里的 `;` 会被 Spring 的 SQL 脚本切分器截断 | `h2-probe-dashboard2.txt` |
| v3 | `create alias ... for "类.方法"`（引用已编译类） | **通过**。最终选了这个更稳的形式 | `h2-probe-dashboard3.txt` |

**⭐ 最值钱的一条实测结论**：`dateSub` 的第二个参数**必须声明成 `String`**。

| 声明类型 | 结果 |
| --- | --- |
| `int` | `Data conversion error converting "INTERVAL '6' DAY"` |
| `Object` | `Hexadecimal string contains non-hex character` |
| **`String`** | **成功**——H2 把 `interval 6 day` 解析成 `INTERVAL '6' DAY` 后**原样当字符串传进来** |

另有一条小坑：`FOR` 子句要**双引号标识符**，用单引号会报
`Syntax error ... expected "identifier"`（`h2-probe-dashboard3.txt` 有记录）。

**设计上的两个自我约束**（写在代码注释里）：
1. `parseDays` **只支持 DAY 单位**，也**只翻译生产 SQL 用到的 9 个格式符**——出现别的一律**抛异常**。
   宁可让用例红灯，也不能悄悄返回错误的值把断言变成**假绿灯**。
2. 安装动作**必须幂等**（`create alias if not exists`）——同一个 H2 内存库
   （`DB_CLOSE_DELAY=-1`）被整个测试 JVM 的所有用例类共用，安装会被反复触发。

**实证**：DB-04 期望的 `Total: 3`（今天 / 3 天前 / 6 天前三个分组，**窗口外的第 7 天被正确剔除**）
在构建日志里真实出现，且 SQL 原文与生产 XML 逐字一致。

## 4. 人工修改点（本栏最值钱，6 条，全部真实发生）

### 修改点 1 ⭐ —— **看板从"已记录容忍"改判为"已覆盖"，且没有碰生产代码**

- **AI（上一轮的我）的原结论**：H2 不支持 `date_format` / `date_sub` → 看板"刻意只碰 LabRepair/LabAsset/LabRoom，未假装覆盖看板"，登记 D-19 容忍。
- **问题**：这个结论**没穷尽**。H2 支持 `create alias ... for` 注册自定义函数，而**MySQL 函数名恰好可以成为 H2 的函数名**。当时只试了"直接跑 SQL"就下了结论，**把"我没找到办法"写成了"做不到"**。
- **人工改为**：先写**探针**（3 版，纯 Java + H2 Shell，不进 `src/test`）实测能力边界，确认可行后再写正式用例。
- **如何验证**：构建日志里出现生产 mapper XML 的 SQL 原文 + `Total: 3`（期望值）。
- **纪律点**：**修的是测试侧，生产 `LabDashboardMapper.xml` 一字未改** —— 这是 T2 卡第 4 节最硬的一条。

### 修改点 2 ⭐ —— `date_sub` 第二参数的类型，试错 3 次才对

- **AI 原方案**：按直觉把第二参数声明成 `int days`。
- **问题**：H2 先把 `interval 6 day` 转成 `INTERVAL '6' DAY` **字符串**再往参数上转 → `Data conversion error`。
  改成 `Object` 更糟：`Hexadecimal string contains non-hex character`。
- **人工改为**：声明成 **`String`**，在函数体里自己解析（`parseDays`）。
- **如何验证**：DB-01 自检用例断言 `date_sub(date '2026-01-10', interval 6 day)` = `2026-01-04`。
- **教训**：**类型不匹配时不要猜，要看错误消息里 H2 实际传了什么** —— `INTERVAL '6' DAY` 这个形态就直接写在报错里。

### 修改点 3 —— 子类定义了**与基类同名但值不同**的常量，会静默遮蔽父类

- **AI 原方案**：在 `LabDashboardIntegrationTest` 里新定义 `REPAIR_PENDING = "0"`、`REPAIR_FINISHED = "3"` 等常量。
- **问题**：`AbstractLabIntegrationTest` 基类**已经有同名常量**，子类的定义会**遮蔽**父类。更糟的是我当时给的值与基类**不一致** —— 一旦有人改了基类的值，子类用例会**继续用旧值静默通过**。
- **人工改为**：删掉子类的重复常量，改用基类已有常量；只有基类**没有**的 `REPAIR_REJECTED = "4"` 才在子类补。
- **如何验证**：`grep -n "static final String REPAIR" src/test/.../integration/*.java` 确认无重复定义。

### 修改点 4 —— **不改写**原有的 5 个反射用例，而是**新增**一组公开入口用例

- **AI 原方案**：接到 D-07 遗留后，第一反应是"把 5 个反射用例直接改成走 `updateLabRepair`"。
- **问题**：那样会**同时删掉已有断言**——反射版直接验证 `validateStatusChange` 的 4 合法 + 16 非法 + 幂等矩阵，粒度比入口版更细。删掉等于**回退覆盖率**，违反 T1 轮"不弱化已有断言"的既有边界。
- **人工改为**：**保留反射版**（契约层），**新增** `LabRepairStatusMachinePublicEntryTest`（入口层）。
  两层职责写进类注释：契约层验证矩阵完整性，入口层验证分支与持久化编排。
- **如何验证**：49/49 全绿，且新增的 3 个用例里有 2 条**只有入口层才可能发现的问题**（见修改点 5）。

### 修改点 5 —— 入口层用例里，**加了卡没要求的"参数级"断言**

- **AI 原方案**：合法流转只断言"没抛异常"。
- **问题**："没抛异常"太弱 —— 状态算错了、资产传错了也照样不抛异常。
- **人工改为**：加强为 **`verify(labRepairMapper).updateLabRepair(argThat(...))`**，断言**目标 status 与旧 assetId 真的被交给持久层**；
  非法流转则断言 **`verify(labRepairMapper, never()).updateLabRepair(...)`**（整轮零写库）。
  另把"状态不变时履历记的是「维修信息更新」而非「状态流转」"也写成断言。
- **如何验证**：3 个用例首次构建即绿；断言粒度可回指 BR-01 与 BR-04。

### 修改点 6 —— 素材包里**必须如实写两件"不好看"的事**

- **AI 原倾向**：素材包只写"49/49 全绿、BR 全覆盖"，看起来更漂亮。
- **问题**：有两条事实**必须写进去**，否则是**不实表述**：
  ① **行/分支覆盖率百分比出不来**（离线仓库缺 `jacoco-maven-plugin` 与 `org.jacoco.core`，只有运行时 agent）；

- **如何验证**：`docs/大作业/AI留痕/测试素材交付.md` §3.2 与 §4.3。

## 5. 顺带定位的一个环境根因：WMIC / PpidChecker（**不为修，为不被误读**）

| 项 | 内容 |
| --- | --- |
| **现象** | 每次构建末尾出现 `System.exit() or native command error interrupted process checker.` + `IllegalStateException: Cannot use PPID 4052 process information. Going to use NOOP events.`，并在 `target/surefire/` 留下 `jvmRun1.dump` |
| **排查路径** | 先怀疑是测试挂了 → 但 `Tests run: 49, Failures: 0` 就在报错上方 → 再看 `PpidChecker.checkProcessInfo(PpidChecker.java:155)` → 顺藤摸到它要靠 **WMIC** 查父进程存活 → 单独跑 WMIC 验证被安全策略拦截（`probe-wmic.txt`） |
| **结论** | Surefire 2.22.2 在 Windows 上查父进程用 WMIC；被拦后它**自己降级为 NOOP events**，属**预期内的退化路径**。**测试不受影响**（49/49 全绿、BUILD SUCCESS） |
| **处置** | **不修**（改了反而可能引入不确定性）。只在留痕与交付文档里写明，避免被误读成"构建有问题" |
