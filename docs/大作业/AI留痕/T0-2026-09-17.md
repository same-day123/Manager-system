## 4. 人工修改点 ← **最重要的一栏**

> 本卡的特殊之处：**要"人工审查"的对象不是 AI 写的代码，而是 AI 写的任务卡本身。**
> T0 卡（含字段清单）由 AI 起草，人工审查时查出 5 处与事实不符或考虑不周的地方。

### 修改点 1：卡里的字段类型/长度与真实库不一致（卡错，不是代码错）

- **AI 原方案**：T0 卡写着 `price decimal(12,2)`、`repair_cost decimal(12,2)`、`room_id bigint not null`。
- **问题**：从**正在运行的 `education_system`** 用 `show create table` 导出的真实 DDL 是
  `decimal(10,2) default '0.00'`、`room_id bigint default null`。
  卡里的字段清单声称"已从 mapper XML 核对"——**但 mapper XML 里没有类型信息**，
  类型是 AI 自己按经验"估"的（12,2 比 10,2 更常见）；`not null` 更是凭空加的。
  后果：若照卡写，`laboratory_schema.sql`、T2 的 H2 建库、真实 MySQL 会变成**三套不同的表结构**，
  架构文档的 ER 图必然与其中一个对不上。
- **人工修改为**：**以真实库为准**（阿辉定），脚本写 `decimal(10,2) default '0.00'`、`room_id` 可空。
  并在脚本末尾新增「与线上库的差异」段，把 6 条差异和取舍理由逐条写明。
- **如何验证**：`select hex(...)` 与索引清单逐条比对（见第 3 节实测输出 3）；
  空库重建后 `information_schema.columns` 与线上库对齐。

### 修改点 2：卡把"能被唯一索引拒绝"这个真缺陷，写成了"不要建唯一索引"的风格建议

- **AI 原方案**：卡里写「不要建唯一索引。原因：本系统用逻辑删除，唯一索引会让"删除后重建同编号"直接失败」，
  并在索引约定里只给普通索引。
- **问题**：结论对，**但只做了一半——卡没有说要处理真实库里已经存在的那两个唯一键**
  （`uni_asset_code` / `uni_repair_code`）。新脚本不建唯一索引，可线上库那两个键还在，
  缺陷依旧存在，而且变成"脚本与线上库不一致"的新问题。
  另外卡还漏了一层：这个冲突不是"风格差异"，而是会**真的返回 500**
  （应用层 `checkAssetCodeUnique` 带 `del_flag='0'` 放行，数据库拒绝）——
  卡里没写这一层，评审时容易被当成可选项。
- **人工修改为**：新建独立幂等迁移 `laboratory_index_fix.sql`，用 `information_schema` 判存在后
  `drop index`，并**在真实库上执行**（连跑两次验证幂等）；同时在脚本注释里把 500 的完整路径写清楚。
- **如何验证**：事务内跑「建 → 逻辑删 → 重建同编号」，修复前会失败、修复后成功（第 3 节实测输出 3）。

### 修改点 3：卡把报修种子数据安排在 `laboratory_demo_seed.sql`，但那里**拿不到演示账号**

- **AI 原方案**：卡的验证要求是"`laboratory_demo_seed.sql` 的演示数据能全部插入成功"，
  隐含把新增种子都放在这个脚本里。
- **问题**：报修单要挂申请人与维修人。6 个演示账号是在 `laboratory_user_seed.sql`（`[5/7]`）才创建的，
  而 `laboratory_demo_seed.sql` 是 `[4/7]`——**排在它前面**。
  两个后果：① 只能写死 `user_id`（若依 `sys_user` 是自增主键，新库上必然错位）；
  ② 更致命的是，**报修列表对非处理角色是按 `applicant_id` 过滤的**
  （`LabRoleUtils.canHandleRepair`），工单不挂在 `student1` 名下，
  学生助管登录后一张都看不到，**US「查看本人报修」在答辩时当场演示不出来**。
- **人工修改为**：房间种子（5 条）留在 `demo_seed`（必须插在 25 条资产**之前**，否则资产的 `room_id` 悬空）；
  **报修种子挪到 `laboratory_user_seed.sql` 末尾**，用 `join sys_user u on u.user_name = 'student1'`
  按用户名解析，不写死 ID。
- **如何验证**：空库重建后 `lab_repair.applicant_name = 学生助管`、`repair_user_name = 维修工程师`；
  `repair_cnt = 4`。

### 修改点 4：卡的验收条件不足以发现问题（"插得进"≠"数据对"）

- **AI 原方案**：卡的通过标准是「零报错 + `lab%` 恰好 5 张表 + `lab_room`/`lab_asset` 的 count 均大于 0」。
- **问题**：这个标准**恰好放过了 D-13**。`lab_asset.room_id` 没有外键，
  25 条资产的 `room_id` 指向不存在的房间时，INSERT **照样成功**，
  `count > 0` 照样成立——但列表页的「所属实验室」整列为空，数据是坏的。
  **AI 把"能插入"当成了"列类型与数据关系都正确"的充分条件。**
- **人工修改为**：验收加三条——`select count(*) from lab_room` 必须 ≥5、
  房间数必须覆盖资产引用的 `room_id` 集合、以及**人工打开一次资产列表页看「所属实验室」是否有值**。
- **如何验证**：空库重建后 `room_cnt = 5`，`lab_room` 的 1001~1005 覆盖了资产引用的 1001~1004。

### 修改点 5：`create_time` 用固定日期会让首页两张图恒为 0

- **AI 原方案**：真实库里 4 条报修的 `create_time` 是 2026-06-27 ~ 07-03，
  照抄即最"忠实"。
- **问题**：`LabDashboardMapper.xml` 的「报修趋势」「维修费用趋势」写死了
  `create_time >= date_sub(curdate(), interval 6 day)`（近 7 天）。今天是 2026-09-17，
  照抄固定日期 → 两张图**永远是空的**，答辩演示时看着像功能坏了。
- **人工修改为**：`create_time` 改用**相对当前时间**（前 1~5 天）；`repair_code` 仍取固定值以保证幂等。
  这点与线上库现状并不冲突：线上 3001 的单号日期（07-02）与其 `create_time`（06-30）本来就不同。
- **如何验证**：`select date_format(create_time,'%Y-%m-%d')` → 2026-09-12 / 13 / 15 / 16，全部落在 7 天窗口内。

### 顺带值得一提的一处自我纠错
