## 3. 关键设计决策（含为什么补了卡外的两个文件）

### 3.1 `deploy/mysql-init.sh` —— 顺序坑，以及两个卡没提的隐藏风险

卡的判断是对的：MySQL 官方镜像按**文件名字母序**执行 `/docker-entrypoint-initdb.d/` 下的脚本，
把 7 个 `.sql` 直接挂进去会得到 `laboratory_demo_seed` 开头、`ry_20260417` 结尾的顺序，
**每个脚本都报「表不存在」**。产出里用显式 `for` 列表锁死顺序，并用脚本自身头部的 `[N/7]`
标记做**三方互校**（脚本顺序 ↔ 磁盘文件 ↔ 文件自称的序号，`t4_verify.py` 第 C 组）。

在此之上我另处理了**两个卡没提到的风险**：

1. **刻意不使用 `set -e`。** initdb 目录下的 `.sh` 若**没有执行位**，官方 entrypoint 是
   `. "$f"` **source** 进来的（而不是当子进程执行）。`set -e` 会顺着漏进 entrypoint
   自己的 shell，之后影响它自己的后续流程。改成 `die()` 显式失败，行为在「被执行」与
   「被 source」两种情况下**完全一致**。
2. **root 连接方式实测一次再决定。** initdb 阶段 root 到底要不要口令，**取决于基础镜像
   版本内部的流程顺序**，各版本不一致。脚本先试免密、再试 `MYSQL_PWD`，都不通才 `die`。
   这样换镜像 tag 不会「忽好忽坏」。
3. 口令用 `MYSQL_PWD` 环境变量传，不写 `-p<password>` —— 口令不会出现在进程列表里被 `ps` 看到。
4. 末尾加**自检**（`lab_*` 表 ≥5 且 `sys_user` ≥1），不达标直接让容器失败 ——
   「容器起来了但一登录就报表不存在」这种半死状态拖到答辩现场最难收场。

### 3.2 为什么补 `docker-compose.prod.yml`

卡第 2 节没把它列进交付内容，但卡 **§1 目标**写了「可以用 `docker-compose.yml` 与
`docker-compose.prod.yml` 的 override 形式具象化」、**§3 边界**又写了「生产 override 文件里要删掉」
—— 不产出这个文件，这两句话就落空了。

实现上有一处**必须知道的坑**：Compose 对 `ports` 这类多值字段的默认合并规则是**拼接**，
所以**在 override 里没法「删掉」基础文件的端口**。用 Compose v2.24+ 的 **`!override`** 标签才是
「替换」语义（文件头已写明版本要求与退路）。

### 3.3 为什么补 `.env.example` 并改 `.gitignore`

卡 §3 边界要求「一律用 `${VAR:-default}` 形式并配 `.env`（`.env` 要加进 `.gitignore`）」。

改 `.gitignore` 时有个**很容易踩的雷**：不能写 `.env.*`——那个通配符会把
`RuoYi-Vue3/.env.development` / `.env.production` / `.env.staging` **一起忽略掉**，
而它们三个是 vite 的**构建期**配置（`VITE_APP_BASE_API=''/prod-api''` 就在里面），
一旦被忽略，前端构建出来的 API 前缀就错了。所以只精确忽略 `.env` 与 `.env.local`，
并在 `.gitignore` 里写了这条警告。

**验证过**（不靠"看起来对"）：`git check-ignore -v .env` 命中，而
`git check-ignore -q RuoYi-Vue3/.env.production` **未命中**。

## 4. 人工修改点（**AI 报告「人工审查」章节素材**）

> 卡第 7 节明确要求列这一节。以下 6 条都是**真实发生**的：AI/卡产出物本身有缺口或错误，
> 靠「核对真实配置」拦下来。第 4.1、4.2 两条可直接写进 AI 报告。

### 4.1 ⭐ 卡给的可用环境变量清单漏了 redis 主机/端口 → 照抄会得到一个「能启动但登不进去」的容器

卡第 4 节列的可用环境变量是 `RUOYI_DB_URL` / `RUOYI_DB_USERNAME` / `RUOYI_DB_PASSWORD` /
`RUOYI_REDIS_PASSWORD` / `RUOYI_TOKEN_SECRET` / `RUOYI_DRUID_*`，**没有 redis 的主机与端口**。

但 `application.yml:71,73` 是：

```yaml
  redis:
    # 地址
    host: localhost
    # 端口，默认为6379
    port: 6379
```

**写死，连 `${}` 占位符都没有。** 容器里后端进程的 `localhost` 指向它自己，不是 redis 容器。
照卡执行的结果非常有欺骗性：

- 容器**起得来**（Lettuce 连接池是懒连接，启动时不建连）；
- 后端镜像自带的 `HEALTHCHECK`（探 8080 端口）**也能过**；
- 但 `/captchaImage` 一被调用就 Redis 连接异常 → **登录页的验证码永远出不来**
  （前端只显示一个空验证码框，不会报"Redis 挂了"）→ 答辩演示的第一个动作就卡死。

**处置**：用 Spring Boot **原生变量名** `SPRING_REDIS_HOST=redis` / `SPRING_REDIS_PORT=6379`
覆盖。原理是 relaxed binding 会把 OS 环境变量映射到同名配置键，且**优先级高于** `application.yml`
（Spring Boot 官方属性源顺序：OS 环境变量 > 应用配置文件）。

**这里的关键判断是：我选择了不碰配置文件。** 卡 §3 边界明写「**不要**为了容器化去改
`application.yml` / `application-druid.yml`」——加 `${}` 占位符虽然也能解决问题，
但违反了边界；用原生环境变量名则**既解决问题又不改一行配置**，与边界完全一致。

**实证**（`t4_env_binding_check.py`，两套不同取值对照）：

```
场景 A（与 compose 一致）: raw:spring.redis.host=localhost   →  eff:spring.redis.host=redis
场景 B（换一组取值）    : raw:spring.redis.host=localhost   →  eff:spring.redis.host=redis-alt
                          raw:spring.redis.port=6379       →  eff:spring.redis.port=6381
```

`raw` 两遍都是 `localhost`（**配置文件确实没被改**），`eff` 跟着环境变量走（**覆盖确实生效**）。

### 4.2 ⭐ 卡给的 `nginx.conf` 示例缺 `client_max_body_size` → 照抄会「传不上故障照片」

卡 §2.2 的 `nginx.conf` 示例里没有 `client_max_body_size`。nginx **默认只有 `1m`**，
而本项目的上传链路是：

| 环节 | 限制 |
| --- | --- |
| 前端 `image-upload` | 单图 5MB |
| 后端 `spring.servlet.multipart` | `max-file-size: 10MB` / `max-request-size: 20MB` |
| **nginx（默认）** | **1m** ← 最紧的一环，卡在最后面 |

所以**上传 1MB 以上的故障照片会被 nginx 直接拦成 HTTP 413**，而且请求**根本没到后端**——
`docker compose logs lab-backend` 里干干净净，前端只弹一个「上传失败」。
这与卡 §5 踩坑表里列的「`proxy_pass` 末尾斜杠」是同一类问题：**症状离根因很远**。

**处置**：`nginx.conf` 的 server 级与 `/prod-api/` 级各补一处 `client_max_body_size 20m`，
并在注释里写清三个环节各自的限制，说明为什么取 20m。

### 4.3 卡给的 `useradd -m -u 1000 ruoyi` 在部分基础镜像上会失败

卡的 Dockerfile 片段是 `useradd -m -u 1000 ruoyi`，之后 `chown -R ruoyi:ruoyi`。
`useradd -m` **不保证**创建同名用户组（是否创建取决于 `/etc/login.defs` 的 `USERGROUPS_ENAB`），
组不存在时 `chown ruoyi:ruoyi` 会以 "invalid group" 失败、镜像直接构建不过。

**处置**：改成**显式两步** —— `groupadd -g 1000 ruoyi && useradd -m -u 1000 -g 1000 -s /bin/bash ruoyi`。

### 4.4 时区：MySQL 容器不能用命名时区

`--default-time-zone=Asia/Shanghai` 看起来很自然，但 MySQL 的**命名时区要求先导入时区表**
（`mysql_tzinfo_to_sql`）——容器里没有，写名字会**直接启动失败**报 `Unknown or incorrect time zone`。

**处置**：改用**数字偏移** `--default-time-zone=+08:00`。这一项对看板是必要的：
`LabDashboardMapper` 用 `date_format` / `date_sub` 按日期聚合，MySQL 留在 UTC 会让
「今日 / 近 7 天」的窗口整体偏移（也正好是 D-25 那张空图所在的查询）。

### 4.5 `.gitignore` 差点写成 `.env.*`

见第 3.3 节。一次「顺手写通配符」就会把 vite 的三个构建期 `.env.*` 一起忽略掉。
已用 `git check-ignore` 正反两面实测，没有只靠肉眼判断。

### 4.6 nginx.conf 写完后带了个 UTF-8 BOM（自查发现）

写文件时开头混进了 `EF BB BF`。**nginx 的配置解析器不容忍 BOM**，会拒绝加载该文件
（`unexpected "" in ...`），容器直接起不来。同理 `deploy/mysql-init.sh` 若有 BOM，
`#!/bin/sh` 的 shebang 会失效；若有 CRLF，容器内 `/bin/sh` 会报 `\r: not found`。

**处置**：逐字节核过，**全部产出文件零 BOM、零 CRLF**（`t4_verify.py` 第 C / F 组各有一条断言守着）。
这条已写进 `t4_verify.py` 的断言里，后续改动会一直被挡住。

### 4.7 一处**卡是对的、差点被我改错**的地方

`maven:3.9-eclipse-temurin-8` 这个 tag 看着可疑（Maven 3.9 一般配 JDK 17），
卡也写了「不存在就退到 temurin-17」。**联网核实后确认该 tag 真实存在**（还有 `-noble` 变体），
所以按卡保留，没有降级。**教训：卡让你"如果不行就退"时，要先确认"是不是真的不行"。**

**第二层：环境变量绑定实证 —— `.workbuddy/tools/t4_env_binding_check.py` + `T4EnvBindingProbe.java`，23 条断言，PASS 23 / FAIL 0**

这一层是**替代 `docker compose up` 最关键的一步**：容器化真正的风险不在 Docker 本身，
而在「环境变量到底能不能盖住写死的配置」。这一点完全可以用**真实的 Spring 属性源机制**在本地证明
——因为跑容器时用的就是同一套机制。

探针加载**本仓库真实的** `application.yml` + `application-druid.yml`，建两个视图：

- `raw:` = 只加载配置文件（剥掉 `systemProperties` / `systemEnvironment`）→ 看「写死的是什么」
- `eff:` = 完整属性源（`addLast` 追加配置文件 = 最低优先级，与 Spring Boot 一致）→ 看「最终生效什么」

然后**跑两遍不同取值**（A 与 compose 逐字一致；B 全部换掉）做对照：

| 断言类别 | 结果（选摘） |
| --- | --- |
| **配置文件没被改过** | A、B 两遍 `raw:ruoyi.profile=D:/ruoyi/uploadPath`、`raw:spring.redis.host=localhost`、`raw:token.secret=abcdefghijklmnopqrstuvwxyz` 全部一致 |
| **覆盖生效** | A：`eff:ruoyi.profile=/home/ruoyi/uploadPath`、`eff:spring.redis.host=redis`、`eff:spring.datasource.druid.master.url` 指向 `//mysql:3306/education_system`、`eff:token.secret`/`eff:spring.redis.password`/`eff:swagger.enabled=false` 均为注入值 |
| **对照排除"碰巧相等"** | B：`eff:ruoyi.profile=/srv/other-uploads`、`eff:spring.redis.host=redis-alt`、`eff:spring.redis.port=6381`（**而 `raw` 仍是 6379** —— 证明端口也受环境变量控制） |
| **类型化绑定**（容器里后端真读的就是这个类） | `bind:spring.redis.port.type=Integer`；`spring.redis` 整块绑成 **`RedisProperties`**：`host=redis` `port=6379` `database=0` `timeout=PT10S`（`10s` → `Duration` 转换成功）；B 场景跟着换成 `redis-alt:6381` |

**这一层的价值**：它把「后端在容器里能不能连上 `redis` / 写得了 `/home/ruoyi/uploadPath`」
从「看图说话」变成了**可复现的断言**，而且不需要 Docker。
