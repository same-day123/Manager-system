| --- | :-: | --- |

| ⭐ 内联 `key idx_xxx (col)` | **✅ 可用** | 建表脚本原样保留，未改成独立 `create index` |

## 3. 人工修改点（AI 报告素材，6 条，全部真实发生）

### 修改点 1 ⭐ —— **卡外的第 5 个文件**：生产 `application.yml` 的 `spring.profiles.active: druid` 会污染测试配置

- **风险来源**：`src/main/resources/application.yml` 第 55 行写着 `spring.profiles.active: druid`。
  一旦 druid profile 被激活，`application-druid.yml` 就会加载，把数据源描述成
  MySQL（`driverClassName: com.mysql.cj.jdbc.Driver` + `druid.master.url=jdbc:mysql://localhost:3306/education_system`）。
- **为什么这个失败模式比"测试报错"严重得多**：
  本机没起 MySQL → 构建失败（至少是响的）；**本机正好起着 MySQL → 这 7 个用例会连到开发库
  `education_system` 上，而 `@BeforeEach` 会 `delete from lab_room / lab_asset / lab_repair`，
  等于把演示数据清空**。这是一个"静默失败会毁掉演示数据"的配置。
- **处置**：在 `src/test/resources/` 放一份最小的 `application.yml`（测试资源在 classpath 上优先于主资源），
  只写 `spring.profiles.active: integration`，把生产那份遮住。**这是卡里没有的第 5 个文件。**
- **⭐ 但我做了对照实验，结果推翻了"这是必需项"的假设，必须如实记下来**：

  | 实验 | 命令 | 结果 |
  | --- | --- | --- |
  | 有遮蔽文件（交付态） | `mvnx.ps1 -o -B clean test` | `The following 1 profile is active: "integration"`，37/37 绿 |
  | **移出遮蔽文件** | `mvnx.ps1 -o -B clean test -Dtest=LabAssetIntegrationTest` | **仍然是 `The following 1 profile is active: "integration"`，2/2 绿** |

  → **结论：`@ActiveProfiles("integration")` 本身就压住了配置里的 `spring.profiles.active`，
  遮蔽文件不是"缺了就过不去"的必需项，而是一层防御。**
- **保留它的理由（写进了文件头注释，供后人判断）**：上面那个失败模式的代价过高（清掉演示库），
  而多这一份文件的代价极低，属于宁多一道保险；文件头已写明「若将来要删，请先重跑那条对照命令确认行为未变」。
- **已知副作用（已接受、已记注释）**：测试期不再读生产 `application.yml`，于是只有生产那份里定义的
  占位符在测试 banner 里解析不出来，表现为 `Application Version: ${ruoyi.version}`。
  纯显示层；已 grep 核实 **laboratory 包内没有任何 `@Value` / `@ConfigurationProperties` 依赖生产配置项**，无功能影响。
  对照实验里移出遮蔽文件后该行变成 `Application Version: 3.9.2` —— 这也反过来**证明了遮蔽确实生效**。
- **更值钱的一点**：我第一次写这个文件时，注释里写的是"`@ActiveProfiles` 是**附加** profile 语义，不覆盖配置里的值"。

### 修改点 3 —— 卡说"最小上下文只装配 DataSource + MyBatis"，**实测 Druid 与 Quartz 也进来了**

- **实测证据**（`t2-run2-final.log` 第 67~77 行）：

  ```
  INFO  c.a.d.s.b.a.DruidDataSourceAutoConfigure - [dataSource,68] - Init DruidDataSource
  INFO  c.a.d.p.DruidDataSource - [init,865] - {dataSource-1} inited
  INFO  o.q.s.RAMJobStore - [initialize,155] - RAMJobStore initialized.
  ```

- **为什么无害**（逐条查证过，不是"跑起来了就算没事"）：
  - **Druid**：`DruidDataSourceWrapper` 的 `afterPropertiesSet()` 在 `spring.datasource.druid.*` 没配 URL 时

    所以 Druid 只是把 H2 包了一层连接池，**数据仍然落在 H2 上**。
  - **Quartz**：默认 `spring.quartz.job-store-type=memory` → `RAMJobStore`，**不建表、不连库**。
    卡担心的"Quartz JDBC JobStore 要连库建表"在这个上下文里**不会发生** ——
    真正会把它切到 JDBC JobStore 的是 `com.ruoyi.framework.config.ScheduleConfig`，而它不在扫描范围内。
- **处置**：**没有**追加排除项。理由是它已经跑通且零外部依赖（启动约 3 秒），
  为了"日志更干净"去偏离卡已定的方案不划算。但我**把这件事实写进了
  `LabIntegrationTestApplication` 的类注释**，并明确写了「不要据此宣称上下文里只有 DataSource + MyBatis」——
  避免后人拿卡的说法当事实复述。
- **净效果**：上下文启动约 3 秒、零中间件依赖，达成卡的原始目标。
