## 3. 交付物与验收结果

### 3.1 `ci.yml` 的 job 结构

| job | 阶段 | 关键配置 | 产物 |
| --- | --- | --- | --- |
| `backend` | 后端构建与测试 | `actions/setup-java@v4` → `temurin` / `'8'` / `cache: maven`；`defaults.run.working-directory: RuoYi-Vue-fast`；`mvn -B clean test` | `backend-surefire-reports`（`if: always()`，失败时报告更要留） |
| `frontend` | 前端生产构建 | `actions/setup-node@v4` → `'22'` / `cache: yarn` / `cache-dependency-path: RuoYi-Vue3/yarn.lock`；`corepack enable` + `yarn install --frozen-lockfile` + `yarn build:prod` | `frontend-dist`（`RuoYi-Vue3/dist/`） |
| `package` | 打包可运行 jar | `needs: [ backend, frontend ]`；`mvn -B package -DskipTests` | `backend-jar`（`target/ruoyi.jar`） |
| `docker` | 镜像构建 | **整段注释保留**，等 T4 产出 Dockerfile 后取消注释；凭据走 `secrets.REGISTRY_*` | —— |

其它要点：触发 `push: [main]` + `pull_request` + 手动 `workflow_dispatch`（答辩演示可直接手动跑一次，不必为了触发而提交代码）；`concurrency` 取消同分支上的旧运行；`permissions: contents: read` 最小权限；**测试阶段绝不加 `-DskipTests`**；**yml 内不出现任何明文密码**。

**为什么 CI 用 JDK 8 而不是本机离线构建用的 17**：`pom.xml` 里 `java.version=1.8`、生产运行镜像也是 Java 8，CI 与运行时保持一致；同时避开 Mockito 3.9.0 在新 JDK 上的字节码增强问题。

**为什么缓存不写 `cache-dependency-path: pom.xml`**：项目是单模块，`cache: maven` 直接可用，无需额外路径。

## 4. 人工修改点（《AI 辅助开发实践报告》素材）

> 这一节是本轮最有价值的部分：**每一条都是"AI 写出来的东西在本机/本仓库跑不通，由人判断后改掉"的真实案例。**

| # | AI 的初版 / 卡里的写法 | 问题 | 人的判断与改法 |
| :-: | --- | --- | --- |
| 1 | 卡第 4 节提示词给的前端命令：`node RuoYi-Vue3/node_modules/vite/bin/vite.js build --mode production` | **在仓库根执行必失败**（12ms 报 `Could not resolve entry module "index.html"`）：vite 的 `root` 取的是**当前工作目录** | 改为在脚本里 `Push-Location RuoYi-Vue3` 后再 `node node_modules/vite/bin/vite.js build --mode production`，`finally { Pop-Location }`。**这是调用姿势问题，不是代码问题**——单独按正确姿势跑 `exit=0 / 67.9s` |
| 2 | 卡里提示「优先 `corepack enable && yarn install --frozen-lockfile`」 | 仓库只有 `yarn.lock`、**没有 `package-lock.json`**，`npm ci` 会直接失败 | 采纳 yarn 路线，并把「若 `--frozen-lockfile` 因 lockfile 与 package.json 不同步而失败 → 改用 `npm install` 并在同一次提交补上 `package-lock.json`」写进 yml 注释，留给后人 |
| 3 | AI 初版用 `& powershell ... 2>&1 \| Out-File $log` 抓 Maven 输出 | **PowerShell 5.1 会把原生命令 stderr 包成 `NativeCommandError` 再吐回本进程 stderr**；外层一旦用管道捕获本脚本，管道因 `RemoteException` 中断，**脚本连同日志一起被干掉**（22:01 那次丢了后半段输出与汇总表） | 改用 **Maven 自带的 `-l <文件>`** 落盘，主流程**全程无管道**。附带好处：`-l` 写出的日志不带 ANSI 色码，更好读 |
| 4 | AI 初版直接读子进程输出 | 中文与 `✓` 全变乱码（`鉁?`）——PowerShell 解码原生命令输出走 `[Console]::OutputEncoding`，本机默认 GBK | 脚本开头同时设 `[Console]::OutputEncoding` 与 `$OutputEncoding` 为 UTF-8，**并额外剥掉 vite 的 ANSI 色码**（落日志要干净）。改前改后：`鉁? 2545 modules` → `✓ 2545 modules transformed.` |
| 5 | AI 初版汇总表用 `Measure-Object -Property Secs -Sum` 求总耗时 | 本机对 `List[object]` 会抛 `ArgumentException`，导致总耗时一栏**空白** | 换成显式 `foreach` 累加。**教训：汇总表是给人看的，它自己崩了最丢人** |
| 6 | AI 初版汇总表用 `PadRight` 对齐 | 中文是**双宽字符**，`PadRight` 按字符数补齐 → 表格歪掉 | 自写 `Get-DisplayWidth`（CJK 计 2 列宽）+ `Format-Cell`，按**显示宽度**补齐 |
| 7 | **AI 初版把「`/captchaImage` 非 200」直接判 FAIL** | 本机 Docker 不可用 → 流水线**没能自己启动服务**，此时 8080 上若恰好有别的后端（别的会话起的）在响应 502，**被误判成本流水线的失败**，整条流水线 `exit 1` —— 而卡明确允许阶段 6 是 `SKIPPED` | 判据改成：**只对"流水线自己启动的服务"判失败**。docker 不可用（阶段 5 SKIPPED）→ 阶段 6 无论探测到什么一律 `SKIPPED`，把观察到的 HTTP 码作为**说明行**打印，不计入失败。这条改完，验收标准（阶段 1–4 PASS、5/6 允许 SKIPPED）才真正达成 |
| 8 | AI 初版把日志攒到结尾一次性落盘 | 进程被外部中断时**全部丢失**（第 4、5 次运行就丢了） | 改为 `StreamWriter` + `AutoFlush` **逐行即时落盘**，进程被杀也不丢已产出内容 |
| 9 | AI 初版对并行构建冲突无处理 | 多会话共用 `RuoYi-Vue-fast/target/`，一方 `clean` 的瞬间另一方在写 class → 报 `Cannot create resource output directory` / `Error assembling JAR` / `写入 ...IdUtils.class 时出错`。**这些是假失败**，但会让验收反复不过 | 新增 `Test-TargetConflict` + `Invoke-MavenStage`：识别冲突特征后**最多重试 3 次**（间隔 5s），并在输出里写明「本机另有会话在跑 Maven」 |
| 10 | AI 初版把错误摘取写成「取最后 4 条 `[ERROR]`」 | Maven 的**最后几行永远是模板话术**（`Re-run Maven using -X` / `[Help 1] http://…`），把**真因挤掉** | 改为先剔除模板行再取前 3 条，真因（如 `Error assembling JAR: …SysConfigMapper.class`）才露出来 |

## 5. 过程中定位并登记的新偏移

### D-26：沙箱拦 WMIC 会**概率性**掐断整棵命令树（已记录容忍）

| 项 | 内容 |
| --- | --- |
| 现象 | 同一份 `local-pipeline.ps1` 连跑 **7 次**：第 3、5、6 次完整跑到汇总表，**第 4 次死在阶段 3（vite 构建）中途且无任何报错**（日志只到 `transforming...`） |
| 根因 | Surefire 2.22.2 的 `PpidChecker` 在 Windows 上要调 **WMIC** 查父进程存活（根因已由「测试负责」在 `AI留痕/T2b-2026-09-17.md` 第 5 节钉到类与行号）；本机安全策略把 WMIC 拉黑 → 沙箱抛「PROGRAM BLOCKED」事件 → **连带杀掉正在运行的整条命令链**。触发点在**阶段 2（Maven 测试）**，但被杀的往往是几秒后的阶段 3 |
| 排查路径 | 先怀疑 vite → **单独跑 vite 构建 `exit=0 / 67.9s`，排除**；再怀疑管道捕获 → 换 `-l` 后仍偶发，排除；最后定位到「凡是跑了 Maven 测试的那次命令，工具调用就返回 WMIC 拦截事件」——**7 次运行里含测试阶段的全都出现过该事件** |
| 能否从构建参数规避 | **不能**。可关闭 `PpidChecker` 的 `ProcessCheckerType` **只存在于 Surefire 3.x**（已解包本机 `mvn_repo` 下的 `surefire-booter-{2.22.2,3.1.2,3.5.3,3.5.5}.jar` 逐个比对确认）。**不为绕沙箱去升 surefire** —— 那会改动测试执行方式，代价大于收益 |
| 处置 | **记录容忍，不改代码**。缓解：① Maven 阶段自愈重试；② 日志即时 flush；③ **跑不通就重跑**（第 3 次即成功）。**CI（GitHub Actions / Linux）无此问题** |
| 影响面 | 只影响本地自检体验。答辩截图**必须先本地跑通再截**，别在截到一半的图上将就 |
