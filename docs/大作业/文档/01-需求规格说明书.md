## 1 引言

### 1.1 编写目的

本文档描述「高校实验室资产与报修管理平台」的软件需求，是后续架构设计、编码实现、测试用例编写与结课验收的共同依据。
预期读者包括本组成员、授课教师与验收人员。文档中的每一条用户故事都对应系统中已实现的接口与页面，不留"纸上功能"。

### 1.2 项目背景

高校二级学院的实验室日常有两套并行的管理动作：一是**资产台账**，二是**设备报修**。当前两者的落地方式都存在明显缺口：

| 现状做法 | 由此产生的问题 |
| --- | --- |
| 台账用 Excel 手工维护，分散在若干个人电脑里 | 设备的调拨、报废没有留痕，学期末盘点时账实不符，且查不出是哪一个环节出的错 |
| 报修靠微信群喊人 | 报修人不知道单子走到了哪一步，维修方也不清楚当天有哪些活；催办只能靠反复询问 |
| 维修费用记在个人记录上 | 一学期修了多少次、哪台设备最常坏、花了多少钱，都拿不出统计口径 |

因此本项目把"台账、工单、统计"三件事收进同一个系统：让每一次资产变动都留下可追责的履历，
让每一张报修单都有明确的状态与责任人，让每一个学期都有可直接交付的运维数据。

### 1.3 术语与缩写

| 术语 | 说明 |
| --- | --- |
| 资产台账 | 记录全部实验设备的编号、名称、类型、价格、归属实验室与状态的清单 |
| 报修单 | 一次设备故障上报及其处理过程的数据载体 |
| 履历 / 时间线 | 资产或报修单的状态变动流水，含操作人、操作时间与备注 |
| 逻辑删除 | 删除时只把删除标记置为已删除，数据库记录保留，列表默认不再显示 |
| AC | Acceptance Criteria，验收标准 |
| GWT | Given-When-Then，验收标准的书写格式 |
| INVEST | 用户故事的六条质量准则：Independent / Negotiable / Valuable / Estimable / Small / Testable |
| BR | Business Rule，业务规则；本项目共 6 条，是测试用例的判定依据 |

## 2 产品愿景板

| 维度 | 内容 |
| --- | --- |
| **愿景陈述** | 让每一台实验设备都有人管、有账查、有维修记录可回溯——学院实验室的资产与故障处理，不再依赖个人记忆和 Excel |
| **目标群体** | 学院实验室中心的在岗教师（总责）、各实验室的房间管理员、兼职的学生助管、设备处或学院派驻的维修人员、负责固定资产卡片的行政人员、以及需要查看运维情况的学院督导 |
| **核心需求（用户痛点）** | ① 台账变动无痕、期末对不上账；② 报修进度不透明、催办靠人；③ 维修费用与故障分布没有统计口径；④ 新购设备入库录入量太大；⑤ 不同岗位看到的数据范围应当不同 |
| **产品（核心功能）** | 实验室房间维护 · 资产台账（含 Excel 批量导入导出、二维码标签、全生命周期履历）· 设备报修闭环（提交 → 审核 → 维修 → 完成 → 评价，含故障照片与维修成本）· 运维工作台（4 项指标 + 4 张分析图）· 基于角色的菜单权限与数据行级过滤 |
| **商业价值** | 把实验室资产与运维从"个人表格"升级为"有履历、有责任人、可统计"的组织资产：盘点时间由半天量级压缩到分钟量级，故障处理的每一步可被追踪，学期末可直接产出运维数据用于预算与考核 |

## 3 用户角色分析

系统在权限层面共设有 7 个角色。按**使用动机**归并后，可得到下面 5 类使用者。
每类使用者看到的数据范围不同：只有"可查看全部数据"的角色能看到全量工单与看板，其余角色被强制过滤为本人数据。

### 3.1 报修申请人

| 项目 | 描述 |
| --- | --- |
| 对应权限角色 | 学生助管、房间管理员 |
| 角色描述 | 实验室的日常使用者与兼职管理的学生，负责所在房间设备的日常巡视与报修 |
| 核心目标 | 设备坏了能在一分钟内报上去，并且随时知道处理到哪一步 |
| 痛点 | 设备编号靠手抄容易错；报上去之后不知道进度、只能反复追问；维修质量好坏没有人记录 |
| 数据可见范围 | 仅本人提交的报修单 |

### 3.2 维修执行方

| 项目 | 描述 |
| --- | --- |
| 对应权限角色 | 维修工程师、维修教师 |
| 角色描述 | 学校设备处或学院派驻的维修人员，同时承担带教任务 |
| 核心目标 | 一次看全所有待办工单并按故障等级排优先级；修完把实际成本如实登记 |
| 痛点 | 工单靠群消息派发容易漏；看不出哪台设备是反复修的；费用记在本子上，期末汇总不出来 |
| 数据可见范围 | 全部报修单、全部资产 |

### 3.3 实验室管理员

| 项目 | 描述 |
| --- | --- |
| 对应权限角色 | 实验室管理员 |
| 角色描述 | 学院实验室中心的在岗教师，对全院实验室资产与运维负总责 |
| 核心目标 | 台账准确、工单闭环、随时能拿出运维数据向学院汇报 |
| 痛点 | 房间、资产、报修三份 Excel 互相对不上；无效报修占用维修资源；上级要数据时只能临时统计 |
| 数据可见范围 | 全部资产、全部报修、运维看板 |

### 3.4 资产管理员

| 项目 | 描述 |
| --- | --- |
| 对应权限角色 | 资产管理员 |
| 角色描述 | 负责固定资产卡片、盘点与报废手续的行政人员 |
| 核心目标 | 每台设备从入库到报废的每一步变动都有据可查；盘点时能一次导出全量台账 |
| 痛点 | 调拨、报废不留痕，账实不符时定位不到责任环节；新购设备入库靠手工逐条录入 |
| 数据可见范围 | 全部资产与全部报修，但对报修单**只读**、无处理权限 |

### 3.5 观察者与系统管理员

| 项目 | 描述 |
| --- | --- |
| 对应权限角色 | 实验室观察员、超级管理员 |
| 角色描述 | 观察员为学院督导或上级检查人员，只查不改；超级管理员负责账号、角色与菜单配置 |
| 核心目标 | 观察员：不动任何数据也能看清全院运维状况；管理员：给不同岗位配不同角色，各人只看该看的 |
| 痛点 | 观察员向各部门要数据太慢；管理员一旦配错权限，会出现"按钮看得见、点下去报 403" |
| 数据可见范围 | 观察员为全部数据只读；超级管理员为全量 |

### 4.2 验收标准（Given-When-Then）

为 6 个核心故事编写了验收标准（任务要求不少于 5 个）。

#### US-01 扫码报修

**场景 1｜扫码带出设备信息**
- **Given** 报修申请人已登录系统，且目标资产当前状态为"正常"
- **When** 该申请人扫描该资产二维码打开报修页并填写故障描述后提交
- **Then** 系统自动填充资产编号与名称，生成的报修单状态为"待审核"，并新增一条"提交报修"的履历记录

**场景 2｜对维修中的资产再次报修**
- **Given** 该资产状态已是"维修中"（前一张报修单尚未结单）
- **When** 申请人对该资产提交报修
- **Then** 系统提示"该资产当前不可报修"，且不生成任何报修单

#### US-03 查看报修进度

**场景 1｜正常查看**
- **Given** 存在一张已经历 3 次状态流转的报修单
- **When** 申请人打开该报修单详情
- **Then** 时间线按时间正序显示"提交报修 → 状态流转 ×3"，每条记录均含操作人与操作时间

**场景 2｜越权查看他人单据**
- **Given** 申请人 A 登录，目标报修单由申请人 B 提交，且 A 不属于可处理报修的角色
- **When** A 直接访问该报修单详情接口
- **Then** 系统拒绝访问并返回"没有权限访问该报修单"

#### US-05 维修方查看全部工单

**场景 1｜处理角色可见全量**
- **Given** 以维修工程师身份登录，库中存在 3 张由不同申请人提交的报修单
- **When** 打开报修列表
- **Then** 3 张全部可见

**场景 2｜普通角色仅见本人**
- **Given** 以报修申请人身份登录，库中存在本人 1 张、他人 2 张报修单
- **When** 打开报修列表
- **Then** 仅返回本人那 1 张

#### US-08 审核报修申请

**场景 1｜审核通过**
- **Given** 报修单状态为"待审核"
- **When** 实验室管理员点击"通过"
- **Then** 状态变为"待维修"，并新增一条状态流转履历

**场景 2｜拒绝申请**
- **Given** 报修单状态为"待审核"，其关联资产已被联动置为"维修中"
- **When** 实验室管理员点击"拒绝"
- **Then** 状态变为"已拒绝"，且关联资产状态恢复为"正常"

**场景 3｜跳过中间环节**
- **Given** 报修单状态为"待审核"
- **When** 试图直接把状态改为"已完成"
- **Then** 系统抛出"非法的报修状态流转"，数据库不发生任何变更

#### US-09 台账筛选与导出

**场景 1｜按房间筛选导出**
- **Given** 台账中存在房间 A 的 3 台设备与房间 B 的 2 台设备
- **When** 资产管理员筛选"房间 = A"并执行导出
- **Then** 导出的 Excel 仅包含 A 的 3 条记录

**场景 2｜已删除资产不出现在导出结果中**
- **Given** 房间 A 的 3 台设备中有 1 台已被逻辑删除
- **When** 导出该房间的资产
- **Then** 导出结果只有 2 条

#### US-12 阻止误删仍有设备的房间

**场景 1｜房间下仍有设备**
- **Given** 房间 A 下有 2 台设备
- **When** 管理员执行删除房间 A
- **Then** 系统提示"实验室下存在资产，不能删除"，房间与设备均不受影响

**场景 2｜房间已清空**
- **Given** 房间 B 下没有任何设备
- **When** 管理员执行删除房间 B
- **Then** 删除成功，且为逻辑删除（数据记录仍保留在库中，仅删除标记被置位）

## 5 非功能需求

> **说明**：本项目的非功能指标**未做专门的性能压测与安全渗透测试**。

| 类型 | 需求描述 | 指标 | 现状与证据 |

| **可维护性** | 规则单一来源 | 同一业务口径只允许有一处定义 | 已实现：状态常量、角色判定、状态机校验各自收敛到单一类；改动时须同步的落点已在开发文档中列明 |
| **可维护性** | 自动化测试 | 核心业务规则有自动化用例覆盖 | **部分满足**：现有 7 个单元测试集中在报修状态机与两类删除约束；提交校验、评价规则、权限判定尚无覆盖（已列为待补项） |

## 6 需求评审：INVEST 自评

| 原则 | 符合情况 | 说明与改进方向 |
| --- | --- | --- |
| **Independent 独立** | ⚠️ 部分符合 | US-01 与 US-03 同处报修主流程；US-01 还依赖台账中已有资产数据（即 US-09/US-10 的产物）。这三条无法完全独立交付，作为一条完整业务链理解更合适。 |
| **Negotiable 可协商** | ✅ 符合 | 故事只约定"用户要什么"，未写死实现方式。例如 US-05 只要求"按故障等级排序"，排序字段与呈现形式仍可与教师、维修方协商调整。 |
| **Valuable 有价值** | ✅ 符合 | 14 条均指向第 1.2 节列出的真实痛点（台账无痕、进度不透明、费用无统计），无"为做而做"的功能。 |
| **Estimable 可估算** | ✅ 符合 | 每条故事都能对应到明确的接口与页面，工作量可按"接口 + 页面 + 校验"拆分估算；无技术不确定项。 |
| **Small 足够小** | ⚠️ 部分符合 | US-13（运维工作台）一条里塞了 4 项指标与 4 张图，颗粒度偏大。改进方向：拆为"指标卡"与"趋势图"两条故事，便于分别验收。 |
| **Testable 可测试** | ✅ 符合 | 6 个核心故事的验收标准均写成 GWT，且判定依据可落到数据库字段（如资产状态、删除标记）与接口返回上；业务规则编号 BR-01~06 可直接被测试用例引用。 |

**自评结论**：14 条故事在 Negotiable / Valuable / Estimable / Testable 四方面完全符合；
Independent 与 Small 存在已知短板（如上两行），已在后续迭代中列为改进项，**本期不调整**——理由是这两项短板不影响交付与验收，
而重拆会导致已完成的实现与故事编号对不上。
