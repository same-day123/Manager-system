## 1 引言

### 1.1 编写目的

本文档给出「高校实验室资产与报修管理平台」的测试策略、测试环境、用例设计方法、用例与业务规则的对应关系，以及最终测试结果。所有数字均来自真实执行的 Maven 构建日志（`Tests run` 汇总与逐类耗时），不存在估算值。

### 1.2 测试范围

覆盖自定义业务包 `com.ruoyi.project.laboratory` 的四个模块：实验室房间、资产台账、故障报修（含状态机与履历）、数据看板。若依框架原生模块（系统管理、监控等）不在本项目测试范围内。

### 1.3 通过标准

全量用例 100% 通过（Failures = 0、Errors = 0、Skipped = 0）；每条业务规则 BR-01~BR-06 至少被一个用例的断言命中，且断言对象可指回规则编号。

## 2 测试策略与测试金字塔

### 2.1 比例与理由

| 层 | 用例数 | 占比 | 为什么这么分 |
| --- | :-: | :-: | --- |
| 单元测试 | 33 | 67% | 报修状态机、权限判定、字段校验三块**规则密集、分支多**，需要毫秒级快速反馈；用 Mockito 隔离依赖，专攻「调用契约」 |
| 集成测试 | 16 | 33% | 本系统一次写操作常常**同时落 2~3 张表**（报修单 + 资产状态 + 履历），事务一致性是单测用 Mock 验证不了的；集成测试用真实 SQL 验证「落库结果」 |
| 端到端 | 2 条主流程 | 手工执行 | 只保留「提交报修→审核→完成」「资产台账增删改查」两条演示主流程，由人工在真实环境按步骤执行 |

> **关于端到端占比低**：本项目**没有引入 Selenium / Playwright**，原因有二：一是离线开发环境无法安装浏览器驱动，二是系统体量（4 个业务模块）不足以摊薄 E2E 框架的维护成本。端到端场景由人工按演示路径实测替代（登录、看板、台账、报修闭环四条路径共 73 条接口请求，0 个 4xx/5xx）。这是有意的设计取舍，不是遗漏。

### 2.2 单元与集成的分工边界

| 维度 | 单元测试 | 集成测试 |
| --- | --- | --- |
| 验证方式 | Mockito 隔离依赖，验证方法被调几次、参数对不对 | Spring 上下文 + 真实数据库（H2 内存库），`JdbcTemplate` 直查表验证落库结果 |
| 能发现 | 分支遗漏、边界值错误、异常消息错误、调用顺序错误 | 多表事务不一致、Mapper XML 与表结构不匹配、SQL 方言问题、行级权限过滤失效 |
| 发现不了 | SQL 是否真的执行成功 | 单个方法的边界组合（集成测试慢，不适合穷举） |
| 中间件依赖 | 无 | **无**（H2 内存库，本地跑测试不需要 MySQL / Redis / Docker） |

## 3 测试环境与运行方式

### 3.1 运行命令

```bash
# 本机首选（Maven 启动脚本损坏时走包装脚本）
powershell -NoProfile -ExecutionPolicy Bypass -File .workbuddy/tools/mvnx.ps1 -o -B clean test

# Git Bash 环境等价命令
bash .workbuddy/tools/mvnx.sh -o -B clean test

# 只跑集成测试（调试用）
powershell ... mvnx.ps1 -o -B -Dtest='*IntegrationTest' test
```

### 3.2 环境三前提（缺一条无法复现）

| # | 前提 | 原因 |
| :-: | --- | --- |
| 1 | 必须离线 `-o` | Maven 本地仓库已预热完毕，离线模式保证构建可重复 |
| 2 | H2 版本**必须锁 `1.4.199`** | Spring Boot 2.5.15 依赖管理指向 1.4.200，本机离线仓库没有该版本；不锁版本会报 `Could not resolve dependencies`，极易误判为网络问题。已在 `pom.xml` 以 `test` scope 锁定 |
| 3 | **不需要** Docker / Testcontainers / 嵌入式 Redis | 本机离线仓库没有这些组件；集成测试全部跑 H2 内存库 |

### 3.3 两个踩坑记录

- **验收一律用 `clean test`**：不带 `clean` 时 `target/test-classes` 会残留上一次编译的类，导致 `mvn test` 与 `clean test` 结果不一致——项目在对照实验中因此失效过一轮。
- **集成测试不加 `@Transactional`**：测试类用 `@BeforeEach` 清表 + 铺基线数据，保证用例间互不污染，同时避免事务回滚掩盖「落库是否真实发生」这一被测对象本身。

## 4 单元测试设计（33 个）

### 4.1 用例分布

| 测试类 | 用例数 | 被测对象 | 考察点 |
| --- | :-: | --- | --- |
| `LabRepairServiceImplTest` | 12 | 报修服务 | 状态机合法/非法流转全枚举、字段校验、资产联动、评分边界 |
| `LabAssetServiceImplTest` | 8 | 资产服务 | 唯一性校验、删除保护、批量导入的成败计数 |
| `LabRepairStatusMachinePublicEntryTest` | 3 | 报修公开入口 | 状态机经 `updateLabRepair` 真实入口的分支与持久化编排 |
| `LabRoomServiceImplTest` | 5 | 房间服务 | 房间删除保护、编号与名称必填、编号占用 |
| `LabRoleUtilsTest` | 5 | 权限判定 | 六类角色的处理权/全局可见权矩阵、无登录上下文兜底 |

### 4.2 状态机的两层覆盖

状态机是全系统风险最高的规则（写错会静默放行非法操作），因此覆盖分两层：

- **契约层**（保留的 5 个反射用例）：直接验证 4 条合法流转 + 16 组非法流转 + 幂等（同状态放行）矩阵。缺点是跨过了公开入口。
- **入口层**（新增 3 个用例）：经 `updateLabRepair` 公开入口触发，补上契约层测不到的三件事——合法流转时持久层**真的收到正确参数**、非法流转时**整轮零写库**（`verify(..., never())`）、状态不变时履历记的是「维修信息更新」而非状态流转。

两层并存是有意决策：契约层穷举矩阵、入口层验证编排，互不弱化。

## 5 集成测试设计（16 个）

### 5.1 用例分布

| 测试类 | 用例数 | 覆盖 |
| --- | :-: | --- |
| `LabRepairIntegrationTest` | 7 | 报修全流程落库、非法流转三处不变、行级权限、逻辑删除、终态不可回退/复活 |
| `LabDashboardIntegrationTest` | 7 | 看板 8 条 mapper 查询全部覆盖（4 项指标 + 4 张图表），含 7 天窗口边界 |
| `LabAssetIntegrationTest` | 2 | 跨模块协作（资产↔房间）、批量导入事务与履历 |

### 5.2 看板方言垫片（不改生产代码补齐 H2 方言）

看板 SQL 使用 MySQL 专有的 `date_format()` / `date_sub()`，H2 不支持。本项目的解法：在**测试侧**用 H2 的 `create alias ... for "类.静态方法"` 注册两个**同名等效函数**，生产 mapper XML **一个字都没改**就在 H2 上跑通了全部 8 条查询。垫片放在 `src/test`，不参与生产打包。

一个实现细节值得记录：`date_sub` 的第二个参数**必须声明成 `String`**——H2 会把 `interval 6 day` 变成 `INTERVAL '6' DAY` 传进来；声明成 `int` 报数据转换错误，声明成 `Object` 报十六进制解析错误。垫片自检用例（DB-01）验证的是**函数真的算得出正确值**，而不是只验证注册记录存在。

### 5.3 基础设施自检与数据铺底

每个集成测试类自带 `@BeforeEach` 基线（房间/资产/报修数据），不依赖执行顺序；DB-01 作为基础设施自检用例单独存在，方言垫片失效时第一个红的就是它，便于定位。

## 9 限制与如实说明

以下四条是本测试工作的已知边界，**均照实说明、未作美化**：

1. **行覆盖率 / 分支覆盖率百分比未能产出。** 本项目全程离线构建，本地 Maven 仓库缺 `jacoco-maven-plugin` 与 `org.jacoco.core`，仅有运行时 agent jar，无法生成覆盖率报告；引入 JaCoCo 还需修改 `pom.xml` 构建段，超出测试工作的改动边界。因此本文以**用例↔业务规则追溯矩阵（第 7 章）作为需求维度的覆盖证据**，辅以断言数 177 与交互校验 27 两个可机械复核的统计量，**不给出未经实测的覆盖率百分比**。
2. **构建日志含一段无害噪声。** Surefire 2.22.2 的 `PpidChecker` 会调用 Windows WMIC 查询父进程存活状态，本机安全策略拦截了 WMIC，Surefire 随即自行降级为 NOOP events 并留下一段 `IllegalStateException: Cannot use PPID ...` 堆栈与一个 `jvmRun1.dump` 文件。**该噪声不影响测试**：本轮 49/49 通过、BUILD SUCCESS。在此说明是为了避免读者把这段堆栈误读为构建故障。
3. **事务回滚为间接覆盖。** 「注入异常后断言双表回滚」的直接验证未做：本机离线仓库中 MyBatis Mapper 是 JDK 动态代理，`@SpyBean` 对其生效性存疑，硬造一个假回滚断言不如如实说明。事务完整性目前由 IT-03「非法流转后单据、履历、资产**三处均不变**」间接覆盖。
4. **测试聚焦 Service 与 Mapper 两层。** 29 个生产类中被测试直接触达的核心类 11 个；Controller 层的权限注解通过真实环境端到端实测验证（四条演示路径 73 条接口 0 个 4xx/5xx），Entity 与纯常量/图形工具类不单独编写用例。
